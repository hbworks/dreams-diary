# SPEC v1.7 — 素材の `## コミット` に「Hermes 経由のコミット」を加える

状態: **確定**（2026-11-07）。保持期間は 30 日。

## 背景

v1.5 の `## コミット` は「自分が `patch` / `write_file` で編集したファイルと重なるコミット」だけを
自分の仕事とみなす。`terminal` で行った `git commit`（`sed` や `git mv` 後のコミットを含む）は、
編集ファイルが記録されないため拾えない。

`dreams-diary` のリポジトリには post-commit フック（`scripts/git_commit_log_hook.sh`）が入り、
Hermes 環境（`HERMES_HOME` あり）で行ったコミットを
`$HERMES_HOME/logs/git-commits/<YYYY-MM-DD>.tsv` に 1 行ずつ記録する。
この記録を「自分のコミット」の根拠に加える。

## A. 判定条件（OR）

当日のコミット C は、次のどちらかを満たすとき「自分の仕事」とする（1 件につき 1 回だけ出す）。

- **(a) ログ**: 当日のログ（`logs/git-commits/<当日>.tsv`）に C の sha があり、かつ
  その行の `profile` が自分のプロファイル名と一致する。
- **(b) 編集**: 既存どおり、C の変更ファイルが自分の `patch` / `write_file` の編集と重なる。

## B. 名前の比べ方

`profile` と自分の名前は、`_author_name(home)` と同じ規則で比べる。
日記の `author` と揃えるため。`HERMES_SESSION_PROFILE` が無ければフックは `HERMES_HOME` の末尾名を
書くので、どちらの経路でも同じ名前になる。

## C. 表示

- 行末に根拠の印を付ける: `[log]` / `[edit]` / `[log+edit]`。
- 日記から「どの根拠で自分の仕事と判定したか」が分かるようにするため。

## D. ログが無い・読めないとき

- ログが無い（フック導入前、または Hermes 外）は (b) だけで判定する。
- 読めないときも (b) だけで判定し、素材に「ログを読めなかった」と書く（無言で落とさない）。

## E. 保持（ローテーション）

- ファイルは日付別（`logs/git-commits/<YYYY-MM-DD>.tsv`）。フックは当日のファイルへ追記するだけで、
  既存の行を書き換えない。
- 古いファイルは削除する（保持期間 30 日を過ぎた日付のファイル）。書き換えを伴わないので、フックの追記と競合しない。
- 削除は**素材の生成時**に行う（夜間 cron が毎日走るため確実に回る）。フックは追記だけにし、
  git の commit 中に削除などの副作用を持たせない。
- 読み込みは当日のファイルだけ。1 日分の行数しか素材に入らないので、トークンは少ない。

## F. 既存ログの移行

- 現在の単一ファイル `logs/git-commits.tsv` は 3 行だけ（検証用）。
- 移行は一度だけ行う（日付別ファイルに振り分けて、旧ファイルを消す）。
  旧ファイルの読み取りは互換として残さない。

## G. 既知の限界（README と素材の注記に明記）

- フック導入前のコミットは (a) に当たらない。
- `--no-verify` のコミットは記録されない。
- `HERMES_HOME` が無いコミットは記録されない（Hermes 外のコミット）。
- したがって (a) に当たらないことは「他人のコミット」の証明ではない。(b) に当たらず (a) にも無い
  コミットは `ほかのコミット` に回る。
- 保持期間（30 日）を過ぎた日は (a) の根拠が消える。

## H. 対象

- `dreams-diary` リポジトリのみ（フック導入済みのリポジトリ）。他リポジトリは従来どおり (b) のみ。

## 受け入れ基準（実装時のテスト）

1. (a) だけに当たるコミットは `[log]` で出る。
2. (b) だけに当たるコミットは `[edit]` で出る。
3. 両方に当たるコミットは 1 回だけ、`[log+edit]` で出る。
4. ログの `profile` が自分と違うコミットは (a) に当たらない。
5. ログが無いとき、(b) だけで判定し、その旨を素材に書く。
6. 保持期間（30 日）を過ぎたファイルは削除され、当日と期間内のファイルは残る。
7. 追記と削除が同じ日に重なっても、当日の行は失われない。

## 変えないこと

- 日記本文の 6 節、二人称の禁止、字数の下限、validator の判定。
- validator の `unresolved_hash` は従来どおり全リポジトリで実在確認する。
  自分の仕事から外れたハッシュでも、実在すれば error にならない。
- `ほかのコミット` の件数の数え方（(a) (b) のどちらにも当たらない件数）。

## 決定事項

- **保持期間は 30 日**。過去日の再生成や補填に余裕を持たせる。
- 削除は素材生成時（E 参照）。
- 残るのは、保持期間内のファイルだけ。

## 実装範囲（確定後）

- `scripts/git_commit_log_hook.sh`: 日付別ファイルへ追記。
- `scripts/install_commit_hook.py`: 変更なし（コピー方式のまま）。
- `main.py`: `_commits_material` に (a) の判定と `[log]` / `[edit]` / `[log+edit]` の表示、ログ読み取りの追加。
- `main.py`: 保持期間（30 日）を過ぎた日付ファイルの削除（素材生成時）。
- `tests/test_commit_hook.py` と素材のテスト: 受け入れ基準 1–7。
- `README.md`: 判定条件、限界、保持期間。
- `templates/cron-prompt.md`: 必要なら、コミットの見方の一文だけ。定数は書き写さない。
