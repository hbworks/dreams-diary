# dreams-diary v1.5 仕様（案）— 素材の根拠・読み戻し・秘匿・コミット範囲

状態: **決定済み（Q1〜Q5 回答済み）。実装前の最終確認待ち**。版: `1.4.x` → `1.5.0`（新機能のため第2桁）。

## 背景

企画レビューで見つかった4点を直す。いずれも「日記の中身を、検証できる根拠に結びつける」ための変更。

| # | 問題 | 決定 |
| :-- | :-- | :-- |
| A | 第3節「間違えたこと」の根拠が素材に無い（ツール名の回数とユーザー発言だけ） | ツールの失敗を素材に追加（Q2:1） |
| B | 「借りているもの」「明日の自分へ」が次の実行から読まれない | 前日の第5・6節を未検証の自己申告として素材に入れる（Q1:1） |
| C | 素材 `_material/<date>.md` に秘密情報がそのまま残り得る | 保存・返却の前に既知形式をマスク（Q3:1） |
| D | コミットが全リポジトリ分で、他エージェントの仕事が混ざる | 自分が編集したファイルと重なるコミットだけを「自分の仕事」にする（Q4:1） |
| E | 日記本文に秘密情報が書かれても気づけない | validator に `possible_secret`（warn）を追加（Q5:1） |

変えないもの: 6節の構成、validator の規則、ハッシュの実在確認（検証側は引き続き全リポジトリを探す）、
「本文はエージェントが書く」原則、1 job / profile。

## A. ツールの失敗を素材に追加

出典: `state.db` の `messages`（role=`tool`）の `content` JSON。当日の時間窓内のみ。

失敗の判定（このツール出力で確認できた形のみ。未知の形は失敗扱いにしない）:

| tool | 失敗とみなす条件 |
| :-- | :-- |
| terminal | `exit_code` が 0 でも null でもない、または `error` が空でない |
| patch / write_file | `success` が `false`、または `error` が空でない（`patch` の検証失敗を含む） |
| read_file | `not_found` が true |
| その他 | JSON の `error` が空でない文字列 |

素材に新しい節 `## ツールの失敗（原因は未確認）` を、「会話」の次に置く。

- 形式: `- HH:MM tool — 呼び出しの要約 → 失敗の要約（terminal は最後の有意な行、他は1行目、最大120字）`
- 呼び出しの要約は、同じ `tool_call_id` の assistant `tool_calls` から取る（terminal は `command`、他は `path`、最大80字）。
- 上限: 1日15件。超過分は `（ほか N 件）`。先頭に tool 別の件数を1行置く。
- 0件なら `（失敗は記録されていない）`。
- 失敗＝間違いではない（grep の不一致、TDD の意図した赤）。節の見出しで「原因は未確認」と明示し、
  プロンプトに「原因は素材から読めるものだけ書く。読めなければ第4節」を足す。
- アシスタントの発言の抜粋は入れない（Q2 の選択外）。

## B. 前日の自己申告を素材に追加

`_previous_diary()` が返す直近の前の日記から、第5節「借りているもの」と第6節「明日の自分へ」の本文を取り出す。

- 素材に `## 前日の自己申告（未検証）` を置く。先頭にファイル名と日付、注記
  `事実として引き継がない。今日の素材で裏が取れたものだけ「返した／まだ」と書く`。
- 合計600字で切る。節が無い・日記が無い場合は節ごと省略せず `（無し）` と書く。
- 検証が未通過の日記も入れる（`## 前回の日記の検証` で未通過と分かる）。
- `cron-prompt.md` 手順3を書き換える: 前日の日記は形式の参考にしてよい、を、
  「第5・6節だけは今日の素材と照合するチェックリストに使う。推測（第4節）は引き継がない」に改める。
- 日記本文の全文は素材に入れない。

## C. 秘密情報のマスク

`collect_material` で `body_full` を作った直後、保存と返却の前に1回だけ通す（出口を1か所にする）。
関数は `main.py` に `redact_secrets(text) -> (text, counts)`。

検出する形式（誤検出より取りこぼしを避けるが、一般語は対象外）:

- `sk-...`、`ghp_...` / `github_pat_...`、`xox[abprs]-...`、`AKIA[0-9A-Z]{16}`、`AIza...`
- `Authorization: ...` / `Bearer <token>`
- `-----BEGIN ... PRIVATE KEY-----`（ブロックごと）
- `(api[_-]?key|token|secret|password|passwd)\s*[:=]\s*<8文字以上>`（値のみ置換）

置換は `[REDACTED:<種別>]`。素材ヘッダに `マスク: N 件`（0なら `0 件`）を出す。

限界（README に明記）: 形式が既知のものだけ。自由文の秘密や、短い値は取れない。
`_material/` を保存しない運用（Q3:2）は採らない。

## D. コミット範囲を「自分の仕事」に絞る

author では絞れない（全エージェントが同じ git author で、コミットはユーザーが手で行っている。
terminal 出力にもコミット行 `[main <hash>]` は残らない）。代わりに、**自分が編集したファイル**との重なりで判定する。

自分が編集したファイル = 当日の時間窓の `messages`（role=`tool`、`tool_name` が `patch` / `write_file`）の
結果 JSON のうち、`success` が false でなく `error` が空のものの `files_modified` と `resolved_path`。
読み取り（read_file / search_files）と `workdir` は「触れた」に数えない（読んだだけで自分の仕事にならないため）。
`state.db` はプロファイルごとに別なので、これは他プロファイルの編集を含まない。

判定:

- 探索対象リポジトリ（`discover_repos`）ごとに、当日のコミットを `git log --name-only` で取り、
  **変更ファイルのどれかが「自分が編集したファイル」に一致する**コミットを「自分の仕事」とする。
  比較は絶対パス同士（リポジトリの root + 相対パス）。シンボリックリンクは `Path.resolve()` で正規化して比べる。
- 素材の `## コミット` には「自分の仕事」のコミットだけを出す。
- 末尾に `ほかのコミット: N 件（自分が編集したファイルと重ならない）` を出す。リポジトリ別の内訳は出さず、黙って消えた状態にしない。
- 各リポジトリの打ち切りは「40行」から「20コミット」に変える（`--stat` の行で後半が落ちる問題の修正）。超過分は `（ほか N 件）`。
- 自分の編集が0件の日は `## コミット` に `（自分が編集したファイルはない）` と書き、全コミットを `ほかのコミット` の件数に回す。
- `state.db` が無い・読めない場合は従来どおり全リポジトリを出し、`（編集を特定できないため全リポジトリ）` と注記する。
- **ハッシュの実在確認（validator）は変えない。** 全リポジトリを探し続ける。範囲を絞るのは素材だけ。

既知の限界（README に明記し、プロンプトにも「コミットが無い＝仕事が無いではない」と書く）:

- terminal 経由の編集（`sed`、ヒアドキュメント、`git mv` など）は見えない。terminal だけで進めた日は、仕事が `ほかのコミット` に回る。
- 同じファイルを2つのプロファイルが同日に編集すると、そのファイルを含むコミットは両方の素材に「自分の仕事」として出る。
- 編集した日とコミットした日が違うと、編集日の素材にはコミットが出ない（コミット日の素材では、その日の編集が無いため `ほかのコミット` になる）。

## E. 日記本文の秘密情報検査

`validate_diary` に `possible_secret`（warn）を追加する。C の `redact_secrets` と同じ検出関数を使い、検出ルールを1か所に保つ。

- 日記本文（frontmatter と見出しを含む全文）に既知形式があれば warn。`detail` には種別と件数だけを書き、**値そのものは出さない**。
- warn なので `ok` は変わらない。プロンプト手順7の「warning は内容を確認し、根拠のない記述を残さない」に従う。
- 日記本文の自動マスクはしない（本文を機械が書き換えない原則を守る）。

## 受け入れ基準

1. terminal の `exit_code=1`、patch の `success:false`、read_file の `not_found:true` を含む合成 DB から、3件が `ツールの失敗` に出る。成功は出ない。16件目以降は件数表記に回る。
2. 失敗が0件の日は `（失敗は記録されていない）`。
3. 前日の日記から第5・6節だけが `前日の自己申告（未検証）` に出る。第1〜4節は出ない。日記が無い日は `（無し）`。
4. 合成素材に `sk-`・`ghp_`・`password=...`・秘密鍵ブロックを入れると、保存された `_material/<date>.md` と返却テキストの両方で `[REDACTED:...]` に置換され、ヘッダの件数と一致する。通常の文章は変わらない。
5. 同じ日に2つのコミットがあり、片方は自分が patch / write_file で編集したファイルを含み、もう片方は含まない場合、`## コミット` には前者だけが出て、後者は `ほかのコミット: 1 件` になる。
   read_file だけで読んだファイルを含むコミットは「自分の仕事」にならない。失敗した patch（`success:false`）の対象も数えない。
6. 自分の編集が0件の日は `（自分が編集したファイルはない）` になり、全コミットが `ほかのコミット` の件数に回る。
   「自分の仕事」から外れたコミットのハッシュを日記に書いても、validator は従来どおり実在を確認できる（`unresolved_hash` にならない）。
7. `state.db` が無いときは全リポジトリ＋注記になる。
8. `possible_secret`: 既知形式を含む日記は `ok` のまま `possible_secret`（warn）が出る。`detail` に値が含まれない。通常の日記には出ない。
9. 既存テストがすべて通る。`cli.py prompt --check` が、テンプレートの変更により各プロファイルを drift と報告する（適用は別途、プロファイルごとに許可を取る）。
