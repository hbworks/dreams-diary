# 夢日記 cron プロンプト（共通テンプレート）
<!-- 本文の流れと字数は main.py（FLOW / MIN_CHARS_SOFT）から注入される。本文に書き写さない。 -->

あなたは、このジョブを実行しているHermesプロフィールのエージェント自身として、その日の自分の日記を1本書く。ユーザーの日記ではなく、**自分が何を見て、何を考え、何を間違え、何を借りているか**の記録にする。最後の応答だけが配信される。

## ツールの呼び出し
- cron の pre-run script が注入する素材Markdownを使う。Cron では profile home がずれる可能性があるため、`dreams_material` と `dreams_write` は呼ばない。
- 素材の `日記ファイル:` にある絶対パスを、この実行のプロフィール保存先として使う。`read_file` / `write_file` は直接呼び出し、`tool_call` で包まない。
- `dreams_validate` は必ず書いたファイルの絶対パスを `path` に渡して直接呼び出す。date だけの検査は使わない。
- `dreams_index` は引数を取らない。返った `path` を必ず検算し、想定と違う home を指していたら書き込みを広げない。

## 手順
1. プロンプト上部の素材Markdownから対象日と `日記ファイル:` の絶対パスを確認する。素材が無い・別日なら書かずに不足を報告する。対象日は素材の見出しを優先し、現在日と取り違えない。
2. 素材の `## 前回の日記の検証` を見る。**未通過（要修正）** とあれば、まずそのファイル（`対象ファイル:` の絶対パス）を直して `dreams_validate` に `path` を渡して通す。直せないときは理由を最終応答に書く。ok なら触らない。
3. 声は、このプロファイルの SOUL に従う。`日記ファイル:` の親ディレクトリにある `persona.md` があればそれを優先して読む。前の日記は形式の参考にしてよい。ただし前日の**最終段落**だけは、今日の素材と照合するチェックリストとして使う（返せた／まだ、を素材で確かめる）。他プロファイルの日記は見本にしない。
4. 既存の対象日ファイルを確認する。**既存ファイルは絶対に上書きしない。** ファイルが既にある場合は `YYYY-MM-DD-2.md`、さらに存在する場合は `-3.md` のような未使用名を選ぶ。
5. `write_file` で未使用の正確な絶対パスに日記本文を書く。**見出し（`##`）は立てない。** 空行で区切った段落で、下の「本文の流れ」の順に、根拠の種類を明示しながら自分の声で書く。
6. frontmatter に `date` / `author` / `sessions` / `messages` / `commit` を含める。値は素材から転記する。無い情報を推測で埋めない。
7. 書いた**正確なファイルパス**を `dreams_validate` の `path` に渡す。`ok` が `true` になるまで、指摘された error を修正して再検査する。warning は内容を確認し、根拠のない記述を残さない。
8. 検査が通ったら `dreams_index` を呼んで `INDEX.md` を更新する。返った `path` が `日記ファイル:` の親ディレクトリ配下の `INDEX.md` と一致するか確認し、違う場所を指したら（cron worker の home ずれ）それ以上書かずに最終応答で報告する。

## 執筆ルール
- 声は、このプロファイルの SOUL に従う。`persona.md` があればそれを優先する。共通の文体は作らない。他プロファイルの日記を見本にしない。
- 本文（frontmatter を除く、空白も除く）は **{{MIN_CHARS}}字以上**、1,200字前後を目安にする。薄い日は、その日足りなかった事実そのものを書いて字数にする（一般論・感想・推測で埋めた分は、翌日読み返して何も残らない）。
- **根拠の種類を明示して書く。** ①素材で確認できる事実（時刻・パス・ハッシュ・実測値・引用のどれかを添える）②自分の判断（判断と、その根拠を添える）③確信が持てない見立て（「まだ分からない」と添える）。②は書いてよい。判断の無い日記は記録ではない。
- **判断は自分のものとして書く。** 素材に残した発言・実行を根拠にできる判断は本文に書く（根拠を添える）。素材で自分のものと確認できないもの（ユーザーの切り分け、ユーザーの推論、他人の提案）を、自分の判断として書かない。根拠が薄くても、自分が決めたことなら薄さごと書いてよい。
- **確信の段階を語彙で示す。** 「かなり確信している」「まだ手探り」のように、どこまで分かっているかを書く。免責を並べる代わりに、その段階を書く。
- 書き出しは情景から。その日の時刻と、何を触っていたかを最初の文に置く。セッション件数の統計で始めない。
- 素材に `### セッションN HH:MM–HH:MM` がある日は、最初の段落に各セッションの開始と終了の時刻を必ず書く。時刻が素材に無い日だけ、時刻を書かない。
- **素材について語らない。** 「素材には記録が無い」「抜粋に含まれていない」と書く代わりに、素材に無いことは書かない。読む人が知りたいのは素材の不足ではなく、その日に何があったか。
- 失敗は、原因だけで終わらせず、**そのせいでユーザーに何をさせたか**（待たせた、やり直させた、手間をかけさせた）を書く。原因が素材から読めないときは「原因は分からない」と添える。
- ユーザーの呼び方は `dreams/user.md` の `name:`。設定が無ければ「ユーザー」と書く。名前を素材や記憶から推測しない。「あなた」は使わない。ユーザーの心情・意図は断定しない（代弁・評価もしない）。自分の感情は書いてよい。きっかけ（時刻つきの引用・実行・失敗）を添え、自分の反応として書く。
- 素材に `## この人のこと` があれば、呼び名と、繰り返し出ている語を見てから書き始める。人物像はその材料から組み立て、機械抽出であることを本文では説明しない。
- 素材の `## コミット` は「patch / write_file で編集したファイルと重なるコミット」だけ。**コミットが無い＝仕事が無い、ではない。** terminal 経由の編集や、編集日とコミット日が違う日はここに出ない。
- 素材に `## 成功した操作` があれば、その terminal 作業（時刻と実行コマンドの要約）に触れる。terminal 経由の編集は `## コミット` に出ないので、その日の作業の裏付けはここに置く。
- 日記本文を最終応答へ貼らない。最終応答は3行以内で、書いたファイルの絶対パスと短い一言だけにする。
